# AI Job 产品与技术规划

## 产品目标

面向 2027 届校招，持续回答一个核心问题：**今天有哪些新公司/新岗位出现，其中哪些最值得我优先投，为什么？**

产品不以“自动海投”为目标，而是建立可靠的求职决策闭环：

1. **岗位发现**：多源自动发现公开 2027 届岗位。
2. **官方核验**：尽可能用公司官网/ATS 官方来源覆盖二手来源。
3. **可解释匹配**：根据候选人画像计算 0–100 分并拆解七个维度。
4. **投递优先级**：用 S/A/B 把“高匹配”转成明确行动优先级。
5. **投递管理**：收藏、投递、面试、Offer、淘汰持续追踪。
6. **反馈闭环**：后续利用真实投递结果校准推荐模型。

## 设计原则

- **画像是唯一事实源**：不得为了提高匹配分虚构经历。
- **发现与匹配分离**：后台宽搜负责尽量不漏，前端画像负责精排。
- **官方来源优先**：同一岗位若存在官方和二手来源，优先保留官方来源。
- **来源必须可追溯**：每条岗位保留 `source / sourceType / sourceUrl / verification`。
- **单源故障隔离**：一个招聘站异常不能导致整个刷新失败或岗位池清空。
- **默认不自动投递**：对外提交由用户主动确认。
- **数据层可插拔**：新 ATS / 公司官网统一映射为同一 Job Schema。

## 当前 V1.2 信息架构

- **岗位雷达**：S/A/B 指标卡 + 关键词 / 城市 / 岗位族 / 优先级 / 分数筛选。
- **公司雷达**：公司岗位数量、城市、岗位族、最佳匹配与来源状态。
- **匹配详情**：七维得分、亮点、缺口、硬性风险、来源核验状态。
- **投递看板**：推荐 → 已收藏 → 已投递 → 面试 → Offer → 淘汰。
- **我的画像**：届别、目标岗位、城市、技能、语言、经历、偏好、排除条件。

## 匹配模型

确定性加权规则：

- 岗位方向 28%
- 技能 22%
- 城市 12%
- 经历 12%
- 语言 10%
- 毕业届别 8%
- 工作偏好 8%

### S / A / B

- **S 档**：匹配分 ≥ 85、无硬性排除、且来源为官方招聘官网/API。
- **A 档**：匹配分 ≥ 70、无硬性排除；二手来源高分岗位在官网核验前最高为 A。
- **B 档**：其余岗位，作为备选或观察对象。

这样可以避免“二手来源 + 高关键词命中”被误当成必须优先投递。

## 下一阶段

### V1.3 — JD 与求职材料

目标：从“该不该投”升级为“怎么投更有胜率”。

- JD 职责 / Must-have / Nice-to-have / 关键词结构化。
- 简历证据与 JD 要求逐项映射。
- 一岗一版简历修改建议，不虚构经历。
- 面试问题预测。
- STAR 素材库与岗位要求映射。

### V1.4 — 推荐反馈闭环

- LLM / Embedding + 规则混合匹配。
- 推荐理由附岗位原文证据。
- 根据投递 → 笔试 → 面试 → Offer 转化率校准权重。
- 岗位新增 / 截止 / 失效监控。
- 每日高匹配岗位通知。
- 公司白名单 / 黑名单和重点公司优先级。

## V1.2 交付验收标准

1. `npm run check` 全绿。
2. GitHub Actions 在真实网络环境完成多源刷新。
3. 安克分页能读取多页或明确报告完整性状态，不把首屏冒充全量。
4. EcoFlow 官方源能真实发现岗位；若官网结构变化，失败只影响该源。
5. `live-jobs.js` 自动写回 `main`。
6. S 档岗位必须满足“官方来源 + 高匹配 + 无硬性排除”。
7. README 与本规划和实际代码状态一致。
